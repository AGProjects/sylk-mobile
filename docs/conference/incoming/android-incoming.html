Incoming Conference Call Flow (Android)

Purpose

Describe what happens, in order, when an Android device is invited to a conference while backgrounded or killed — from the FCM push that wakes the native call service, through the incoming-call UI, to the moment the user is in the room with working audio.

The same central fact as iOS applies: a conference is always an outgoing call. The invite is a notification; accepting it means placing an outgoing call into the room. The reconciliation rule is identical too — the UUID the incoming notification carries (the push session-id) becomes the id of the outgoing conference call. One UUID, one call object, one media session, nothing to tear down mid-call.

What differs from iOS is the platform plumbing: there is no CallKit and no RTCAudioSession. Instead Android uses a foreground Service plus a self-managed ConnectionService, and audio routing goes through AudioRouteModule (API 31+) or InCallManager (< 31). See docs/conference/Incoming.html for the iOS counterpart.

Actors

  • SylkServer — sends the FCM data push (incoming_conference_request, with session-id) and the matching conference invite over the websocket.
  • Native call service ([call] [service] in logs) — a foreground Service started by the FCM message. It parses the payload (onStartCommand), shows the incoming UI / full-screen intent, and on accept calls handleAcceptCall and emits an IncomingCallAction event to JS.
  • react-native-callkeep (self-managed) — Android runs in selfManaged mode (options.android.selfManaged = true); we own the call UI. showAlertPanel is a no-op on Android — the native service owns the panel.
  • CallForegroundServiceModule — the single shared foreground service that backs WebRTC media for all live calls. Started in setCurrentCallActive, stopped in endCall — but only when _calls is empty.
  • CallManager.js — platform-agnostic UUID bookkeeping; the unified-UUID reuse path is shared with iOS.
  • AudioRouteModule / InCallManager — audio-mode + routing. Sets MODE_IN_COMMUNICATION during the call and restores MODE_NORMAL after.
  • react-native-sylkrtc — account.joinConference(room, {id}) honours the supplied id (conference.js: this._id = options.id || uuidv4()).

The flow (current, unified-UUID design)

  1. FCM push arrives. SylkServer sends a data message with event = incoming_conference_request and a session-id. That session-id is the call UUID for the rest of the flow. The native call service receives it, logs the audio mode at receipt, and runs onStartCommand with the payload extras (from_uri, to_uri, session-id, notification-id).

  2. Incoming UI. The service posts the incoming-call notification / full-screen intent. (On a locked phone it starts the call activity; if the app is already foreground it skips startActivity.) RNCallKeep.displayIncomingCall is not used — showAlertPanel returns early on Android.

  3. Invite reaches JS — possibly several times. handleConference(callUUID, room, …) runs once per delivery path: the websocket invite, the FCM prep emit, and the service action can each drive it (observed up to three times for one call). Each run records the invite, but the second and later runs clear the previous answer timer before arming a new one — without that, leaked 45 s timers would fire against the live call. Look for duplicate conference invite … clearing previous answer timer (it fired twice in the verified run).

  4. User accepts. The native service’s handleAcceptCall emits IncomingCallAction (ACTION_ACCEPT_VIDEO) → JS routes to /conference and calls acceptCall(callUUID). The answer timer is cleared.

  5. The reuse decision (acceptCall, _incoming_conferences branch). Identical to iOS: the push UUID is recorded in _reusedPushConferences and passed straight into the conference start (conferenceCall(room, {audio:true, video:false, callUUID})). Log: REUSE push UUID <uuid> as outgoing conference to <room> (no placeholder, no 60s endCall).

  6. The UUID becomes the conference call id. callUUID → callKeepStartConference → outgoingCallUUID → Conference.js → joinConference({id: callUUID}) → conference._id. The sylkrtc call’s call.id is the push UUID.

  7. Report active — and start the foreground service. outgoingConference → startOutgoingCall. Because the UUID is in _reusedPushConferences, we skip startCall() and call setCurrentCallActive(callUUID). On Android setCurrentCallActive also starts CallForegroundServiceModule and brings the app forward. Log: reuse incoming push UUID as active conference <uuid> … setCurrentCallActive instead of startCall.

  8. Media establishes. progress → accepted → established. AudioRouteModule takes the session to MODE_IN_COMMUNICATION and routes to the selected device.

  9. Ends as one entity. No placeholder, no 60 s cleanup. On hang-up the single UUID is ended; terminateCall removes it from _calls and clears _reusedPushConferences. Only because _calls is now empty does endCall stop the foreground service, and AudioRouteModule restores MODE_NORMAL.

The foreground-service rule (Android’s audio-session analog)

On iOS the hazard is CallKit deactivating the shared AVAudioSession when a second call ends. On Android the equivalent hazard is the shared foreground service: it backs WebRTC media for every live call and is started once with no reference counting. Tearing it down suspends media under Android’s background-execution limits.

endCall therefore stops the service only when _calls.size === 0:

if (Platform.OS === 'android' && this._calls.size === 0) {
    NativeModules.CallForegroundServiceModule.stopService();
}
This guard predates the unified-UUID change and exists because the old design exhibited the same class of bug: the 60 s endCall(placeholder) hit an unconditional stopService(), killed the service, and Android suspended the still-live conference media — the invitee was dropped from the room ~60 s in. With the unified UUID there is no placeholder endCall at all, so the path that triggered it is gone; the guard remains as defence-in-depth for any genuine multi-call case.

Locked-screen accept

When the call arrives on a locked phone the JS runtime usually isn’t up yet, so the path is different from the foregrounded case — and it had a subtle bug worth recording.

  1. Native shows the call. The FCM push starts the call service; ConnectionService.onCreateIncomingConnection registers the call and the native IncomingCallActivity is shown over the keyguard (showWhenLocked/turnScreenOn). The early IncomingCallPrep wake is dropped (RN not ready → prep event dropped) — expected, it’s an opportunistic latency optimisation.

  2. Accept is pressed. handleAcceptCall runs with phoneLocked: true and emits the ACTION_ACCEPT_VIDEO bridge event. Because the RN context isn’t initialised, ReactEventEmitter stores the event for pull (RN not ready → event stored for pull) rather than emitting it.

  3. The app is launched. The service calls startActivity(MainActivity) (RN app launched for call). MainActivity is showWhenLocked="true" + turnScreenOn="true", so it surfaces over the lock screen and wakes the display.

  4. JS drains the stored accept. When the RN app mounts it registers the IncomingCallAction listener, calls CallEventModule.markRNready(), and pulls CallEventModule.getLastCallEvent(). The stored accept is handed to callEventHandler, which runs the same acceptCall → unified-UUID conference path as the foregrounded case.

The bug (fixed). The service decided whether to launch MainActivity via isAppInForeground(), which on API Q+ checks ProcessLifecycleOwner … isAtLeast(STARTED). On a locked screen the native IncomingCallActivity — same process — is itself resumed, so that check returned true even though the RN host wasn’t up. The service then took the “skip startActivity” branch, the accept stayed stored and was never drained, and nothing happened. Fix: treat a locked phone as not-foreground — appInForeground = isAppInForeground() && !phoneLocked — so MainActivity is always launched on a locked accept. (Native change; needs a full Android rebuild, not just a Metro reload.)
