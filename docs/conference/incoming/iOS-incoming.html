Incoming Conference Call Flow (iOS)

Purpose

Describe what happens, in order, when a device is invited to a conference while the app is backgrounded or killed — from the VoIP push that wakes it, through the CallKit incoming-call UI, to the moment the user is in the room with working audio.

The central design fact: a conference is always an outgoing call. There is no such thing as an "incoming conference call" on the media layer — the invite is a notification, and accepting it means placing an outgoing call into the room. CallKit, however, can only ask the user to accept something it was told is an incoming call. Reconciling those two facts is the whole story of this flow, and the source of a long-standing audio regression that this document also records.

The guiding rule, after the fix: the UUID CallKit shows as the incoming call becomes the id of the outgoing conference call. One UUID, one CallKit call, one audio session — nothing to tear down mid-call.

Actors

  • SylkServer — sends the VoIP push (incoming_conference_request) and, over the websocket, the matching conference invite.
  • iOS / CallKit (PushKit + CXProvider) — requires that every VoIP push immediately report an incoming call or the app is killed; owns the AVAudioSession.
  • react-native-callkeep (RNCallKeep) — the JS bridge to CallKit. Surfaces answerCall, endCall, didActivateAudioSession, didDeactivateAudioSession.
  • CallManager.js — our wrapper around RNCallKeep; owns the call-UUID bookkeeping (_incoming_conferences, _calls, _timeouts, _reusedPushConferences).
  • app.js — callKeepStartConference(), startConference(), outgoingConference(), and the manual-audio setup at boot.
  • react-native-sylkrtc — account.joinConference(room, options); honours a caller-supplied options.id as the conference call id (conference.js: this._id = options.id || uuidv4()).
  • react-native-webrtc — runs in manual audio mode on iOS (set at boot in app.js); the audio unit only starts when we call RTCAudioSession.setAudioEnabled(true).

The flow (current, unified-UUID design)

  1. Push arrives. SylkServer sends a VoIP push with event = incoming_conference_request and a session-id. That session-id is the call UUID for the rest of the flow. iOS hands it to PushKit, which must report an incoming call to CallKit at once.

  2. handleConference(callUUID, room, …). We record the invite in _incoming_conferences, call displayIncomingCall(callUUID, …) to show the native CallKit panel, and arm a 45 s answer timeout (_timeouts) that ends the call if the user never answers.

    The invite arrives twice — once over the websocket and once via the push — so handleConference runs twice for the same UUID. The second run now clears the first run's timer before arming a new one; without that, the first timer leaked and fired ~45 s later against a live call. Look for duplicate conference invite … clearing previous answer timer in the log.

  3. User taps Accept. CallKit fulfils the answer action and fires answerCall → _rnAccept → acceptCall(callUUID). The answer timeout is cleared and the UUID is marked accepted.

  4. The reuse decision (acceptCall, _incoming_conferences branch). Instead of minting a fresh UUID for the conference, we reuse the push UUID:

    • The UUID is recorded in _reusedPushConferences.
    • It is passed straight into the conference start: conferenceCall(room, {audio:true, video:false, callUUID}).
    • Log line: Callkeep: REUSE push UUID <uuid> as outgoing conference to <room> (no placeholder, no 60s endCall).

  5. The UUID flows into sylkrtc as the conference call id. The chain is exact and worth memorising:

    callUUID
  → callKeepStartConference(room, {callUUID})   // app.js: callUUID = options.callUUID || uuid.v4()
  → this.state.outgoingCallUUID
  → <Conference callUUID={outgoingCallUUID}>    // Conference.js
  → account.joinConference(room, {id: callUUID}) // Conference.js:392
  → conference._id = options.id                  // sylkrtc conference.js:663

    So the sylkrtc conference call's call.id is the push UUID.

  6. Conference reports to CallKit — as the call that already exists. outgoingConference(call) → CallManager.startOutgoingCall(call). Because call.id is in _reusedPushConferences, we do not call startCall() (CallKit already has this UUID as an answered incoming call). We call setCurrentCallActive(callUUID) instead, which reports the existing call connected and keeps its audio session. Log line: reuse incoming push UUID as active conference <uuid> … setCurrentCallActive instead of startCall.

  7. Media establishes; audio starts deterministically. The call goes progress → accepted → established. CallKit activates the AVAudioSession → didActivateAudioSession → _rnActiveAudioSession → RTCAudioSession.audioSessionDidActivate() + setAudioEnabled(true). In manual mode this is the only thing that starts the VoIP audio unit, so audio no longer races CallKit activation.

  8. The call lives and ends as a single entity. There is no placeholder and no 60 s cleanup timer. When the user hangs up, the one UUID is ended (endCall → terminateCall, which also clears _reusedPushConferences). Only now, with _calls empty, does didDeactivateAudioSession disable the audio unit.

Net experience: push → native incoming-call panel → Accept → in the room with audio → hang up. A single UUID appears from handle conference through active call to the final end [call].

Audio-session rules (iOS, manual mode)

WebRTC is put in manual audio mode at boot (RTCAudioSession.setManualAudio(true)). The audio unit is then driven entirely from CallKit callbacks:

CallKit eventHandlerAction
didActivateAudioSession_rnActiveAudioSessionaudioSessionDidActivate() + setAudioEnabled(true) — start the audio unit.
didDeactivateAudioSession_rnDeactiveAudioSessionGuarded: if _calls.size > 0, skip and log skip audio deactivate, active calls remain N. Only when no call remains do we setAudioEnabled(false) + audioSessionDidDeactivate().

The guard is defence-in-depth: with the unified-UUID design nothing ends mid-conference, so the guard should not need to fire on this path. It still protects any future multi-call scenario where one call ends while another is live.
