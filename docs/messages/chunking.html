Message Chunking — Design

Split long text messages into several small messages on the wire, then reassemble them on the receiving client into one message. This keeps every SIP MESSAGE small enough to traverse the server stack, while the user still sees a single conversation bubble.

The feature is implemented identically in sylk-mobile and sylk-desktop. It is entirely client-side: no change to SylkServer, OpenSIPS, the SIP MESSAGE format, or the sync protocol.

1. Why

An outgoing chat message is relayed by SylkServer as a SIP MESSAGE. PJSIP (inside python3-sipsimple) serialises the whole message — request line, all SIP headers, the CPIM wrapper, and the body — into a single fixed buffer of size PJSIP_MAX_PKT_LEN. The build sets this to 262144 bytes (256 KB) (see setup_pjsip.py). If the serialised message does not fit, pjsip_msg_print() fails and the send raises:

PJSIPError: Could not send request: Message too long (PJSIP_EMSGTOOLONG)

The intermediate SIP proxy (OpenSIPS) has its own receive-buffer limit (BUF_SIZE, default ~64 KB) that applies in both directions. Rather than depend on any single ceiling, the client caps each message well below all of them and splits anything larger.

Images and files are not inlined — they go as application/sylk-file-transfer attachments. Chunking applies only to user text (text/plain and text/html).

2. Design at a glance

  • Cap. Each outgoing text message's plaintext is capped at MAX_TEXT_MESSAGE_BYTES = 4096 bytes (UTF-8).
  • Split, then encrypt each. Oversized text is split into pieces; each piece is sent as its own message and encrypted independently (PGP). There is no single giant ciphertext.
  • Lossless word-boundary split. Pieces break on whitespace where possible; concatenating them reproduces the original text byte-for-byte.
  • Invisible marker. Each piece is prefixed with a marker built only from zero-width characters encoding {group id, index, total}. It is invisible in every client.
  • Reassembly on receive. The receiver buffers pieces by {sender, group id} and, once all parts are present, stores/renders one combined message.
  • Other clients are unaffected. A client that does not understand the marker simply renders the pieces with a few invisible characters at the front — nothing visible changes.

4 KB is the plaintext soft cap. After PGP armoring the on-the-wire payload is ~1.4× larger, still far below the 64 KB (OpenSIPS TCP) and 256 KB (PJSIP) transport limits. The hard cap exists only so a single huge HTML element can't push one chunk past the 64 KB OpenSIPS ceiling.

4. The split (lossless)

Both splitters are lossless — concatenating the pieces reproduces the input exactly, which is what makes byte-exact reassembly possible — and never split a multi-byte character (iteration is by Unicode code point, so emoji and accented/CJK characters stay intact). The splitter used depends on the content type.

text/plain — word boundaries

splitTextByBytes(str, maxBytes) returns pieces whose UTF-8 size is each ≤ maxBytes:

  • Word boundaries preferred. A piece is broken after the last whitespace; the trailing partial word is carried to the next piece. Whitespace stays on the left piece.
  • Hard cut only when unavoidable. A single token longer than maxBytes (e.g. a very long URL with no spaces) is cut at a character boundary.

text/html — element boundaries

Plain whitespace splitting is wrong for HTML: tags are full of spaces, so a cut can land inside a tag (e.g. in the middle of <code style="font-size: …">), which leaks raw attribute text and breaks the markup. splitHtmlByBytes(str, maxBytes, hardMax) instead splits at element boundaries:

  • Whole "chapters". It accumulates until the soft cap (maxBytes), then keeps going until the current top-level element closes (nesting depth returns to 0) and breaks right after it. Every piece is therefore a whole number of complete elements, so a large document is split into meaningful, self-contained sections.
  • Never splits a tag. A break is only ever placed outside <…>.
  • Pieces may exceed the soft cap. A piece runs past 4 KB as far as needed to finish the current element — bounded by hardMax (CHUNK_HARD_MAX_BYTES ≈ 35 KB plaintext, ~48 KB on the wire).
  • Fallback order for an oversized single element. If one element is larger than hardMax, the break is placed — in order of preference — (1) after a complete top-level element, else (2) right after any closing > tag, else (3) on whitespace, else (4) a character-boundary hard cut as a last resort. Tags are never broken except in case 4 (a single unbroken token bigger than the hard cap, which is vanishingly rare).

Void/self-closing elements (<br>, <img>, <… />) and comments don't change nesting depth, so they never hold a break open.

5. The invisible marker

Each piece's text is encodeChunkMarker(gid, idx, total) + piece. The marker is a prefix built from zero-width code points:

RoleCode point(s)Name
frame openU+2060 U+2061WORD JOINER + FUNCTION APPLICATION
frame closeU+2061 U+2060FUNCTION APPLICATION + WORD JOINER
bit 0U+200BZERO WIDTH SPACE
bit 1U+200CZERO WIDTH NON-JOINER
field separatorU+200DZERO WIDTH JOINER

Layout: FRAME_OPEN · bits(gid) · SEP · bits(idx) · SEP · bits(total) · FRAME_CLOSE, where each integer is its binary representation rendered with the bit-0 / bit-1 code points. gid is a random 24-bit group id generated once per split; idx is the 0-based piece index; total is the piece count.

parseChunkMarker(text) returns { gid, idx, total, body } when text begins with a valid frame (with 0 ≤ idx < total), otherwise null. body is the text with the marker stripped. Because the marker requires the exact double-code-point frame, ordinary text never false-matches.

The marker lives inside the encrypted body (it is part of the plaintext that gets PGP-encrypted), so the ciphertext on the wire is clean PGP and decryption works unchanged on every client.

6. Sending

Only text/plain / text/html over the cap are split; control payloads (metadata, file transfer, PGP keys) are never touched. Both apps share utils.chunkTextForSend(content, contentType), which returns the marker-prefixed pieces (routing text/html to splitHtmlByBytes and text/plain to splitTextByBytes) or null when no split is needed. Each piece is sent as an independent message with its own id and a 1 ms-staggered timestamp so ordering is preserved.

sylk-mobile

The split runs at the top of App.sendMessage() in app/app.js. When chunkTextForSend returns pieces it recurses through the normal sendMessage path per piece (so each is encrypted, saved, and sent on its own).

sylk-desktop

Encryption happens inside sylkrtc's account.sendMessage(uri, content, type), so sending each plaintext piece separately yields "split-then-encrypt-each" for free. Chat.js calls utils.chunkTextForSend(content, type) — which returns the marker-prefixed pieces or null — at both the new-message and edit send sites, then calls account.sendMessage once per piece.

On the sender's own device the long message appears as several bubbles (each piece is stored separately); the recipient sees one reassembled bubble.

7. Receiving & reassembly

A push notification only alerts that new messages exist; it does not carry the pieces (pushes are throttled, so only the first of a burst registers). The pieces are always delivered in full by one of two paths, and reassembly is wired into both:

  1. Live websocket — pieces arrive one at a time while the app is connected.
  2. Journal sync — on (re)connect the server replays the full set in a batch.

Both paths share one buffer helper that collects pieces by {sender, gid} and fires once when all total parts are present, producing one combined message. A 30 second safety timer flushes whatever arrived if a piece never shows up.

sylk-mobile

  • Live: dispatchIncomingMessage() sits between decryption and handleIncomingMessage(); chunk pieces are buffered (_bufferChunk('_chunkBuffers', …)) and the full text is handed to handleIncomingMessage once, which stores a single plaintext row.
  • Journal: incomingMessageFromJournal() decrypts each text piece to read the marker, buffers it (_journalChunkBuffers), and on completion stores one reassembled plaintext row via saveincomingMessageFromJournal(). The large getMessages() render path is untouched.

sylk-desktop

  • Live: incomingMessage() advances the sync cursor per wire piece, buffers chunks (_bufferChunk('_chunkBuffers', …)), and renders the combined message via _renderIncomingMessage().
  • Journal: syncConversations() buffers chunk pieces from the batch (_syncChunkBuffers) and stores one combined message via messageStorage.add(); each piece is still acked (delivery notification) so the server stops resending it.

The combined message reuses the first piece's id, sender, and timestamp. On desktop, where stored messages are sylkrtc Message instances, _combinedMessage() wraps the first piece so its content (and toJSON().content) is the reassembled text while every other field resolves through the original via the prototype chain. The marker is stripped during reassembly, so storage and rendering see a normal, whole message.

8. Delivery & sync semantics

  • Per-piece acks. Each piece is its own SIP message with its own id, so a delivery notification is sent for every piece; otherwise the server would keep replaying un-acked pieces on the next sync.
  • Sync cursor. The last-message-id cursor advances for every wire piece, never regressing to the first piece's id when the combined message is stored.
  • Idempotent storage. The combined message is keyed by the first piece's id; message storage de-dups by id, so a re-delivered/re-reassembled group does not create duplicate rows.
  • At rest. The reassembled message is stored as plaintext, consistent with how live-received text is already stored (and how lazily-decrypted journal rows end up after first render).

9. Compatibility & limitations

  • Non-Sylk / older clients. The marker is zero-width and HTML pieces are whole elements, so a client that does not reassemble shows the pieces as separate, individually-valid messages with a few invisible characters at the front — no visible corruption. Delivery to out-of-network endpoints (e.g. a generic SIP UA) is therefore best-effort, fragmented-but-readable text; that is acceptable by design.
  • Reassembly scope. A message's pieces are expected to arrive fully via one path (all live, or all in the journal batch). Pieces are not designed to be split across both paths.
  • Mobile journal cost. The mobile journal path decrypts each incoming text message to peek for the marker; non-chunk text is otherwise left to its existing lazy-decrypt-at-render behavior, so those are decrypted twice. A future optimization could store the peeked plaintext to decrypt once.
  • HTML hard cut. The HTML splitter never breaks inside a tag except in the single pathological case of one unbroken token larger than the ~35 KB hard cap (no closing tag and no whitespace anywhere in it). Because reassembly restores the exact bytes before rendering, even that is invisible to reassembling clients.
