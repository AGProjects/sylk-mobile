Message Pipeline

How a chat message arrives, is stored, loaded, rendered and updated in the Sylk mobile app.

TL;DR
SQLite→ app.js getMessages()→ state.contactMessages→ props→ ReadyBox → ContactsListBox → ChatBox→ renderMessages → filteredMessages→ GiftedChat

SQLite is the durable source of truth. contactMessages is the single in-memory source of truth for the currently selected conversation only. ChatBox renders from it; it no longer holds its own message store.

1. Data stores

StoreWhereHoldsLifetime
SQL messages table SQLite Every message for every contact (encrypted at rest where applicable). Durable. The source of truth.
mem state.contactMessages app.js state The selected contact's loaded window, sorted newest→oldest (DESC), overlay baked in. Replaced on contact switch; patched on every live event.
mem this.contactMessageIndex app.js instance field Map<_id, message> over contactMessages. Rebuilt whenever contactMessages is rebuilt.
mem state.messagesMetadata app.js state Per-message arrays of side-channel metadata (labels, rotations, replies, location ticks). For the selected contact; updated by handleMessageMetadata().
mem messagesMetadataById / …ByOriginalId app.js (memoised) Derived {label,rotation,reply} lookup maps, keyed by rendered _id and by origin messageId. Recomputed only when messagesMetadata changes.
One conversation at a time. The app holds the selected contact's messages in memory and nothing else. Other contacts live only in SQL; their previews/unread live as scalars on the contact object (contact.lastMessage, contact.unread). The legacy per-uri map state.messages[uri] has been retired.

2. Arrival

incoming WebSocket / Push

1
handleIncomingMessage(message) classifies the payload (drops control/IMDN/conference-signaling types; handles location ticks via handleMessageMetadata()).
2
saveIncomingMessage() persists the row to SQL and bumps the contact's unread / lastMessage scalars. It does not render.
3
If the sender is the selected contact, handleIncomingMessage builds the GiftedChat bubble (sylk2GiftedChat) and calls _appendContactMessage(uri, gMsg).
4
Encrypted bodies arrive ciphertext-first; the bubble is rendered when decryptMessage() resolves and calls _appendContactMessage(uri, msg) (with a dedup-by-id guard).

outgoing User send

1
sendMessage() persists the row (saveOutgoingMessage), optimistically calls _appendContactMessage(uri, message), and ships it over the wire.
2
Multi-device carbons echo back via outgoingMessage(), which also routes through _appendContactMessage (dedup prevents doubles).

journal Server-history replay

At boot/sync, a batch replay walks journal entries, persists to SQL, and edits a local accumulator across many uris in one pass. At the end of the batch it re-derives contactMessages for the selected contact (only if the batch touched it) via _buildContactMessages(). Per-item index mirrors can't see a batched accumulator, so the batch re-derives once.

3. Storage

Every arrival path writes to SQL first; that write is unconditional and independent of whether the conversation is open. The in-memory update is conditional: it only happens when the message belongs to the selected contact (the _append/_patch/_remove helpers no-op otherwise).

Rule. If a message arrives — or a state change occurs — for a uri that is not the selected contact, it is saved to SQL only. When the user switches to that contact, the full view is booted from SQL.

4. Loading

Loading happens on contact switch (and pagination). getMessages(contact, filter):

1
Resolves all of the contact's uris (getAllContactUris) and runs a windowed SQL slice across them (category / pinned / date filters applied in SQL).
2
Converts rows to GiftedChat bubbles (sql2GiftedChat), decrypts inline where needed, builds messagesMetadata, into a local scratch map.
3
Publishes the result: setState({ messagesMetadata, contactMessages: this._buildContactMessages(slice, messagesMetadata) }). _buildContactMessages sorts DESC, bakes the overlay, and (re)builds the id index.

Pagination — “load earlier” calls getMessages with a larger window, which rebuilds contactMessages from the grown slice. Cold-start fast-load shows the just-tapped push bubble first, then the tail, then the full slice supersedes it.

5. Rendering

app.js contactMessages→ prop → ReadyBox→ ContactsListBox→ {...props} → ChatBox
1
ChatBox's _syncStateFromProps (migrated from UNSAFE_componentWillReceiveProps, now driven by componentDidUpdate) sets state.renderMessages from the contactMessages prop. A change-detection merge preserves unchanged bubble refs.
2
componentDidUpdate derives state.filteredMessages from renderMessages: the in-memory filters (size / location / links / date-narrow), date-pill aggregation, local search, and a sort that is skipped when the list is already in the requested order (default desc, no search).
3
filteredMessages feeds GiftedChat (inverted), so newest renders at the bottom.
What ChatBox no longer does: it doesn't keep a message store, doesn't read messages[uri], and doesn't compute the media-label / rotation / reply overlay per render — that's baked upstream (see §7).

6. Updates by id

State changes for an existing message (delivery receipts, read markers, file-transfer progress) patch a single entry through the id index — no array scan to find the message.

EventHandlerMirror
IMDN accepted/delivered/displayed/failed, pin/unpinmessageStateChanged → updateRenderMessageState_patchContactMessage(id, updated)
File transfer progress / play / position / failedfileTransferStateChanged → updateFileTransferBubble_patchContactMessage(id, updated)
Call-trace enrich (tappable call bubble)_enrichInMemoryCallMessage_patchContactMessage(id, patched)
Conference message updateupdateConferenceMessage_patchContactMessage(id, updated)
_patchContactMessage(id, newMsg):
  if (!contactMessageIndex.has(id)) return false;   // not the selected contact → no-op
  contactMessageIndex.set(id, newMsg);
  setState({ contactMessages: arr.map(m => m._id===id ? newMsg : m) });

The index has(id) check doubles as the “is this the selected contact?” test. Membership is O(1); the array rebuild is O(n) because React needs a fresh array reference.

7. Metadata overlay

Labels (media captions), rotations, and replies are transported as separate application/sylk-message-metadata rows and collected in messagesMetadata (keyed by message id, value = array of {action,value,…}). Rather than re-deriving this in ChatBox on every render, app.js owns it:

1
Bake on build: _buildContactMessages calls _overlayMessage(msg, mm) to stamp text (label), rotation, and replyId onto each bubble (last entry per action wins).
2
Re-bake on change: when a metadata tick lands for the selected contact, handleMessageMetadata re-bakes that one message via _patchContactMessage, so it survives the next merge.
3
Lookup maps: messagesMetadataById / messagesMetadataByOriginalId are derived (memoised) and passed to ChatBox. The reply-preview render reads them with a direct id lookup (getMetadataByActionForMessage) — no array walk.
Location is the exception. Live-location bubbles still synthesise their tick text inside ChatBox's componentDidUpdate (the messagesMetadata branch), because the map polyline needs the full ordered tick trail. Baking the location trail app-side is a planned follow-up; until then messagesMetadata still flows to ChatBox for location.

8. Deletes & clears

  • Single message — deleteMessage / deleteRenderMessage(Sync) → _removeContactMessage(id) (SQL delete + index/array removal).
  • Meeting-session wipe — removes every bubble matching a sessionId by filtering contactMessages directly and rebuilding the index.
  • Conversation delete / purge — SQL rows removed; if it's the selected contact the view clears (navigation usually nulls selectedContact too).
  • Reset / call-end / logout — clear contactMessages: [] and contactMessageIndex.

10. Invariants

  • SQLite is the durable source of truth; contactMessages is the in-memory source of truth for the open chat.
  • Exactly one conversation is held in memory. Non-selected events are SQL-only.
  • Every write path persists to SQL and mirrors into contactMessages through one of _append / _patch / _remove (or a _buildContactMessages rebuild).
  • The id index and contactMessages are always rebuilt together.
  • contactMessages is always DESC-sorted with overlay baked; ChatBox does not re-sort (except for asc / active search) and does not re-overlay.
  • ChatBox owns no message store — it renders the prop.
